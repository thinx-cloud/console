AUTH-01 (08-RESEARCH §3.2) and AUTH-02 (08-RESEARCH §3.3) close that gap without changing the backend, without new dependencies, and without touching the access/refresh token swap convention in core/api.js.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query string → PasswordReset.vue computed state | this.$route.query.reset_key / activation / owner flow into hasResetToken and into submitConfirm's payload. Values originate from the user-controllable URL bar (typically pasted from an email link). |
| PasswordReset.vue form state → backend POST | email / password / rpassword from <input v-model> bind directly into the action payloads (after client-side guards for min-length and match). |
| Anonymous Vuex action → core/api $post | requestPasswordReset and confirmPasswordReset use the same $api client as authenticated calls; the client transparently signs requests if a token exists (anonymous request otherwise). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-01-01 | Information Disclosure | reset_key appearing in URL bar / browser history | accept | Backend enforces single-use + short TTL on reset_key (5–15 min standard, cleared by `set_password_reset` on success — owner.js:561-597). The token is intended to ride in the URL (this is the email-link UX); browser-history exposure is the accepted norm for this flow. |
| T-08-01-02 | Tampering | client-side bypass of password validators | mitigate | Client guards (length >= 4 and password === rpassword) run in submitConfirm before the backend call, but they are advisory only — the backend re-validates server-side (owner.js:561-597). A user who tampers with submitConfirm via devtools can only submit a request the backend will reject; no security boundary is crossed. |
| T-08-01-03 | Spoofing | malicious user requests reset email for an arbitrary address | accept | Backend already silently no-ops on unknown emails (owner.js:488-491 returns success=false response='user_not_found' but the same response shape is used for valid emails after enqueuing the send — the timing oracle is the only differentiator and that is a known accepted limit). The client surfaces success=false as "Could not initiate reset." regardless. Rate limiting is the backend's responsibility. |
| T-08-01-04 | Denial of Service | repeated rapid submits flooding the backend | mitigate | The submit button is disabled via :disabled="submitting" for the duration of the in-flight request. This prevents accidental double-submit by the user. Adversarial clients can bypass it but they can already bypass the page entirely by calling the endpoint directly; the backend owns rate limiting. |
| T-08-01-05 | Tampering | activation parameter sent in place of reset_key | accept | The two reset paths share the same /password/set endpoint and the backend chooses the right validator based on which field is present (08-RESEARCH §3.3). The client passes whichever is provided in $route.query. A user pasting a malformed link gets the backend's natural error message surfaced via errorMessage. |
| T-08-01-SC | Tampering | npm supply chain | accept | This plan installs NO new npm packages. vue-jwt-decode is already a listed dependency (08-RESEARCH §1.1) and is not used by Wave 1; no new vendor code is introduced. The legitimacy of pre-existing packages is the project's standing posture. |
</threat_model>
