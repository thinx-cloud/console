<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Profile.vue → profile/deleteAccount action | Owner hash from state.profile.owner flows into the DELETE body; must match req.session.owner on backend |
| Profile.vue → profile/uploadAvatar action | Raw base64 string from FileReader flows into POST body; no server-side size limit is enforced in this version |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01-01 | Elevation of Privilege | deleteAccount — owner from state | mitigate | Backend validates req.body.owner === req.session.owner (router.user.js:119-121). Even if the client sends a different owner hash, the backend rejects it with 403. The frontend reads owner from the authenticated profile state only — no user-editable field. |
| T-06-01-02 | Denial of Service | uploadAvatar — no client-side size limit | accept | This phase does not impose a client-side file size limit. The backend writes verbatim to avatar.json; extremely large files could consume disk. Phase 6 scope does not include file size validation — this is a known accepted risk for a developer console with a known user base. |
| T-06-01-03 | Tampering | uploadAvatar — base64 content not validated | accept | The backend stores the string verbatim. The avatar is displayed via img src= with a data-URI prefix — the browser sandboxes image rendering. No XSS vector from base64 content in an img src. |
| T-06-01-04 | Spoofing | Header.vue My Account link — open redirect | accept | to="/app/profile" is a relative internal router path. BootstrapVue b-dropdown-item with a relative to value cannot produce an open redirect. |
| T-06-01-SC | Tampering | npm supply chain | accept | This plan installs NO new npm packages. |
</threat_model>
