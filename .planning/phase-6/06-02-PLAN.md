      onAvatarFileChange(event) {
        const file = event.target.files && event.target.files[0];
        if (!file) return;
        const reader = new FileReader();
        reader.onload = (e) => {
          const dataUri = e.target.result; // e.g. "data:image/png;base64,AAAA..."
          const commaIdx = dataUri.indexOf(',');
          this.avatarB64 = commaIdx !== -1 ? dataUri.substring(commaIdx + 1) : dataUri;
        };
        reader.readAsDataURL(file);
      },
      async saveAvatar() {
        if (!this.avatarB64) return;
        this.avatarUploading = true;
        const result = await this.uploadAvatar(this.avatarB64);

        if (result && result.success) {

          this.message = 'Avatar updated.';
          this.avatarB64 = null;
        } else {

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FileReader → avatarB64 data field | Browser reads local file; the data-URI prefix is stripped before the base64 payload is stored and transmitted |
| profile.admin flag → Admin tab visibility | Backend-supplied boolean controls DOM presence of admin tab content; v-if (not v-show) ensures removal from DOM |
| saveNotifications → profile/updateProfile | Full info object is spread before the notifications overlay — no user-editable field can inject keys not already present in profile.info |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Tampering | saveNotifications info merge | mitigate | Object.assign spreads existing profile.info then overlays notifications. The info object originates from the backend (fetchProfile) and is not user-editable beyond the three checkboxes. No injection surface. |
| T-06-02-02 | Information Disclosure | Admin tab DOM exposure | mitigate | v-if="profile && profile.admin === true" removes the admin tab from the DOM entirely for non-admin users. A non-admin inspecting DevTools will see no admin content. The profile.admin flag is authoritative — it comes from the authenticated session response on the backend. |
| T-06-02-03 | Tampering | Avatar upload — base64 data from FileReader | accept | FileReader reads a user-selected local file. The base64 string is POSTed to /api/v2/profile which writes it to avatar.json. The backend performs no content-type validation on the avatar string. Malicious content stored as avatar.json cannot cause XSS — it is displayed via img :src with a data-URI prefix that the browser sandboxes. |
| T-06-02-04 | Denial of Service | Avatar upload — no file size limit | accept | No client-side size limit is enforced. This is an accepted risk for Phase 6 scope (developer console, known user base). A note is left in the code for Phase 7+ to add a size check. |
| T-06-02-05 | Elevation of Privilege | Admin tab — read-only, no action buttons | accept | The Admin tab in this phase contains zero action buttons and zero API calls. It displays only read-only profile data already visible in the Account tab. No elevation is possible. |
| T-06-02-SC | Tampering | npm supply chain | accept | This plan installs NO new npm packages. |
</threat_model>
